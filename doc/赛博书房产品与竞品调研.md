# 赛博书房产品与竞品调研

2026 年 11 月 26 日。依据当前仓库、一次合成数据检索测试及下列产品的一手资料。竞品按用户可能用什么替代书房来选，覆盖六类需求、十个代表产品或项目。竞品能力以官方说明为准。用户定位和优先级是待验证的产品判断。

## 一、竞争发生在哪里

| 用户想完成的事 | 可替代产品及其优势 | 对书房的意义 |
|---|---|---|
| 打开电脑，有个愿意待着的房间 | Spirit City 将自定义房间、音乐、精灵、待办、计时、习惯和日记放在一起。它直接争夺用户留在桌面的时间。[开发者商店页](https://store.steampowered.com/app/2113850/) | “有氛围又能做事”已经有成熟参照。更有说服力的演示是隔周回到房间，还能用上上次读过和写过的东西。 |
| 用物件代表真实的自己 | GitHub 上的 3D Portfolio 用可点击房间展示作者经历和作品。[作者仓库](https://github.com/trevsm/3D-Portfolio) | 可逛的房间本身容易复现。书房多了一层持续使用的理由：使用者可以添加自己的内容，物件背后的收藏会增长。 |
| 把不同主题和材料连起来 | Capacities 有对象类型、反向链接、日期和日记；Obsidian 的 Bases 把本地 Markdown 属性变成可筛选的视图，官方 Maps 插件还能标点；思源提供块级引用、数据库和 SQL 查询。[Capacities](https://docs.capacities.io/tutorials/object-types-vs-folders) · [Obsidian](https://obsidian.md/help/bases) · [地图插件](https://obsidian.md/help/bases/views/map) · [思源 GitHub](https://github.com/siyuan-note/siyuan) | 关系、筛选、本地保存、地图均有替代。书房的机会是让用户第一次摘录就自然留下书和原文位置，第一次记旅途就有地点，不需要先设计一套笔记结构。已有成熟笔记库的人迁移动力较弱。 |
| 给书影音留档，发现下一部作品 | 豆瓣有书影音标记、评论和个人档案；NeoDB 的开放目录覆盖书影音、播客、游戏，支持评分、清单和联邦分享。[豆瓣产品说明](https://blog.douban.com/douban/2018/12/29/3917/) · [NeoDB GitHub](https://github.com/neodb-social/neodb) | 公共条目、发现和社区已有优势方。书房更适合回答个人问题，例如“我为什么在那趟旅行反复听这首歌”。 |
| 重访过去，收拢散落的记录 | Day One 有日记地图和“历史上的今天”；Timelinize 可把多个账户和设备的数据汇入本地时间线，也可借助关联补足地点上下文。[Day One 地图](https://dayoneapp.com/features/map-view/) · [往年今日](https://dayoneapp.com/guides/tips-and-tutorials/on-this-day-view/) · [Timelinize GitHub](https://github.com/timelinize/timelinize) | 前者是低成本唤起记忆的标杆，后者是批量导入历史生活的标杆。书房的优势候选是在日常阅读、听歌、写作过程中直接产生可回顾的材料；手工补录越多，这一优势越弱。 |
| 保存很多碎片，日后能找回 | mymind 用浏览器扩展和移动端收集笔记、书签、文章、图片，强调自动整理。[mymind](https://mymind.com/) | “收藏一切”会让用户直接比较采集速度。书房更有机会服务愿意对少量重要材料留下想法、日后重用的人。 |

最接近书房的替代方案可能是一组已有习惯：用 Spirit City 专注，用现有阅读器划线，用日记或笔记软件回顾。用户已经拥有这些工具，因此书房需要证明的是，省下的重复摘抄、切换和翻找，值得用户改变其中一个习惯。现有材料能支持差异化定位，尚不能证明独占性、留存优势或付费意愿。

## 二、书房实际交付什么

当前七个内容区、十二种可独立查找的记录。体验还有三个层次：房间物件和互动菜单提供入口，知识库提供跨区查找、统计、回收与关系查看，当前筛选结果可用于地图或 Markdown 快照。环境音、宠物和植物提供陪伴。内容主要保存在本机，平台音乐和已配置的 AI 服务有各自的连接条件。[功能登记](../src/features/definitions.js) · [项目介绍](赛博书房项目介绍.md) · [操作说明](../README.md)

| 活动 | 能留下什么，之后怎么用 |
|---|---|
| 阅读 | 导入 Markdown、TXT、可提取文字的 PDF、EPUB；留下书、摘录和批注，之后能从笔记找回原文位置。PDF、EPUB 的转换依赖相应本地组件。[导入实现](../electron/books.cjs) |
| 听歌、观影 | 歌单及歌曲可检索、关联，按来源条件播放；影片可记观看状态、类型与评分。影片区定位为收藏管理。 |
| 写日记、随手记事 | 日记记录日期、心情和图文；便签保存想法，待办记录完成状态。三类内容均可进入知识库。 |
| 旅行 | 将照片或文字放到记忆点，把多个点编入旅途；已确认的地点可用于地图回顾。 |
| 抄写 | 保存进行中或已完成的作品；从书中发起时保留来源，可以连同阅读记录回看。 |

**核心卖点：在自己的书房里读、听、写，过一阵子还能从一个地点、一句话或一首歌，找回当时那段经历，并拿它做点新东西。** 对外展示应选一次找回，而非依次点开七扇门。比如用户记不起书名，只记得旅行日记里写过“夜航”；搜出日记，沿自己当时留下的连接找到那条摘录，回到书中读上下文，再把选定的材料整理成游记提纲。三维场景有助于第一次理解和进入，已经积累的记录在第二次使用时才体现价值。

最值得先验证的用户是同时有阅读摘抄、写日记或保存旅行照片习惯，偶尔还会写读后感、游记或年度回顾的人。只需要背景音乐、扫码记账或管理团队任务的人，眼下从这套跨内容能力中得到的收益较少。

## 三、真实生活怎么接进来

| 真实问题 | 今天可以怎么做 | 接入成本和边界 |
|---|---|---|
| 半年前在苏州哪座桥边听到那首歌？ | 导入出行照片，确认桥的位置，编入“苏州周末”；把歌曲与该记忆点关联。下次从地点或歌曲进入，沿关系找另一端。给日记、歌曲等需要一起导出的材料加同一趟旅行的标签，可按标签生成快照。 | 旅途包含哪些点由结构保存；哪首歌与桥有关通常要人确认。标签命中、图上的邻居和快照收录范围各有含义。添加一个关联不会自动给双方加相同标签。 |
| 读了几个月，想写一篇关于城市散步的文章 | 阅读时划线、批注；看片之后登记影片，某次散步写日记。给关键材料统一标记“城市散步”，筛出它们，生成 Markdown。可在已配置的 AI 对话中附上快照，请它按观点归类，再回书中核对。 | 书与摘录的出处天然保留；跨活动的主题仍需要线索。快照保存当时的文字和相应字段，照片、海报和音频不会作为原件附进去。[快照格式](../src/resultApplications/snapshotMarkdown.js) |
| 搬家后管理家电说明书、保修和维修 | 说明书可作为支持格式的读物，购买或维修过程写日记，未完成的事记待办。能先解决“说明放哪了、上次修过什么”。 | 当用户要按设备查序列号、按保修到期日自动提醒、和家人同步处理时，便签维护成本上升。应新增设备和维修记录，另接提醒、共享能力。现有房间新增一个工具箱模型，只能改变入口。 |

**扩展成本取决于改哪一层。** 普通用户用标签、现有类型和手动关联即可组织新主题。场景制作者可按照场景包格式替换房间、模型、热点并绑定已有功能。开发者增加新类型时可以复用目录、搜索、侧栏和结果应用，但仍要接字段、表单、持久化、旧数据、批量操作及回收恢复。增加一种面向现有命中结果的输出，如按月回顾，通常比接入持续变化的外部数据源省力。接相册或日历的持续同步还涉及授权、重复导入、修改、删除和冲突处理。当前普通手动关联也有类型规则，例如两本书之间不能直接建立普通关联，可先用共同标签组织。[扩展手册](项目修改手册.md) · [扩展示例](../src/entities/extension.test.js) · [关联规则](../src/entities/contentRelations.js)

## 四、多到看不过来时

人的负担和机器的负担会在不同时间出现。即使检索立即返回，面对几百条无标题照片，人仍然很难挑出需要的一张。书房目前最擅长有线索的回顾：先用日期、地点名、类型、标签或正文词缩小范围，再在关系图查看命中项的直接邻居，或聚焦一个对象。全局搜索可选书籍全文；复杂语义和未录入的生活背景仍难靠关键词还原。AI 可以分析用户附上的快照，现有流程依赖用户先选择材料。[检索](../src/search/searchCore.js) · [关系图](../src/resultApplications/EntityGraph.jsx) · [AI 材料入口](../src/data/snapshotPrompt.js)

**检索小测。** 使用项目原有关键词查询函数，在内存生成同结构短中文日记，标题不同，每百条有一条正文含“苏州”。预热一次、查询七次取中位数。1,000 条约 1.9 毫秒，10,000 条约 13.2 毫秒，100,000 条约 122.2 毫秒，每档命中数均符合预期。测试以空的标签存储替身运行，未计入真实本地读写、建目录、排序、长书正文、照片、图布局和界面渲染。结果说明短文本过滤随规模增加有可见成本，不能据此承诺十万条的整机体验。[实际查询函数](../src/search/searchCore.js)

代码有两项现成缓解手段：全局检索首批显示 40 条，关系图在节点与边合计超过 320 时按可视区域减少绘制。前者仍要先查询和排序，后者仍要先算布局。普通集合多以 JSON 整组读写，书库与地球仪另存文件，跨区目录需汇总各来源。容量规划至少要区分条目数、正文字数、附件体积和关联密度。[全局搜索](../src/search/GlobalSearch.jsx) · [目录汇总](../src/entities/catalog.js) · [关系图](../src/resultApplications/EntityGraph.jsx) · [本地存储](../src/data/spaceStorage.js)

| 用户所处阶段 | 目前最有用的辅助 | 值得优先补的能力 |
|---|---|---|
| 记得自己在找什么 | 标题、全文、类型与日期条件，直接回原记录 | 验证手机或浏览器快速采集，让人不用回桌面重录 |
| 记得大致时间、地点或一条线索 | 旅途、记忆点、标签、直接邻居、局部图、批量整理 | 保存可重复执行的查询，按时间地点建议关联并由用户确认 |
| 已忘了有什么，或想把多年资料整体迁入 | 对已选材料做快照、交给 AI 整理；对长年混合库尚缺实测 | 主动回顾、可追溯的语义检索、增量索引、全库备份恢复演练；用多年混合库测冷启动、首次搜索、导入中断和恢复 |

## 五、下一步最值得验证的事

先让一批目标用户带自己最近的一次旅行或阅读主题来试。记录三项结果：首次把三种材料放进同一主题需要几分钟、要手工标记几次；隔一周只给地点或一句话，多久能重新找到原文和相关照片；和用户原有工具相比，完成一份可以拿去写作的材料清单省了多少时间。如果建联麻烦，先解决采集和低成本关联；如果找回很快却没人主动回来，先测试周期回顾；如果混合库的打开和查询已影响使用，再用端到端测试决定索引和存储改造顺序。核心假设是用户会反复用到曾在书房里留下的东西。
