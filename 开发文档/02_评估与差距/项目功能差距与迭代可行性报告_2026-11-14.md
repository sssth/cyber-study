# 赛博书房项目功能差距与迭代可行性报告

评估日期为 2026-11-14。评估对象为当前工作目录源码与开发文档中的六份 v1.0 需求。

## 1. 结论与评估口径

当前项目已经具备三维书房、阅读与摘录、平台音乐导入和播放、电影资料获取，以及日记、Memo、抄写等实际功能。下一阶段的主要工作是把这些功能整理为可长期使用、可迁移、可关联的个人内容系统。

六个重点模块的发展阶段不同。电子书、电影和音乐都有可继续建设的基础；个人知识库目前主要围绕书籍摘录；地球仪仍是照片展示原型；学术文献库在当前源码中尚无独立工作台。

本报告分为两部分。第 3 节客观对照需求与代码，第 4–8 节给出我的优先级判断、实现建议、可行性和验收路线。这些建议属于技术评估，不自动成为新增产品需求。

**证据范围**

- 本轮检查了六份需求的功能结构、验收清单、关键决策及相关正文，并对照 React 页面、Electron 服务、存储模型和功能路由。
- “已具备”表示代码中存在相关实现路径。“部分具备”表示尚不足以达到整项需求。“待验证”表示依赖真实账号、外部服务、数据规模或运行环境。
- 本轮是文档与源码评估，没有重新运行完整浏览器验收，没有登录个人平台账号，也没有读取私人日记、照片或账号凭据。
- 既往截图与测试只能证明当时版本。本报告不把旧测试结果当成本轮新版全部功能已经验收。
- 当前代码已经超过 11 月 12 日的改动报告。音乐并非只有手工链接，PDF 也已经具备文字提取入口。

## 3. 客观对照——每个模块要求什么、已有多少、还缺什么

### 3.1 电子书阅读

| 需求组 | 当前实现 | 主要缺口 |
| --- | --- | --- |
| 本地导入 | MD、TXT、文字版 PDF；文件与文件夹入口；批量结果；按文件内容哈希识别完全重复文件 | EPUB；书目与正文分离；跨文件版本关联；ISBN 等书目信息 |
| 文件存储 | Electron 保存原件、book.md 和 book.json，存在旧 IndexedDB 迁移路径 | 多附件／版本模型、统一备份恢复、迁移完整验收 |
| PDF 阅读 | Python 提取文字并转换为 Markdown，拒绝无文字的 PDF | 原页查看、页码与文本映射、图表保留、原页与重排切换 |
| 阅读体验 | 目录、章节、分页相关逻辑、字号行距、进度恢复、摘录与批注 | 五类主题、字体管理、完整排版设置、三种翻页体验、独立书签和统计 |
| 书架 | 已导入与示例书卡片、进度、全文搜索 | 封面书架、正在读／最新导入、待读／正在读／已读、95% 确认、红心、主分类和多书单 |
| 外部来源 | 未发现微信读书、豆瓣已读书目导入流程 | 临时审核、四五星预选、待补正文、重复关联和用户确认 |
| 搜索 | 对现有正文进行关键词匹配，展示章节／片段并跳转 | 当前书／休闲书库／全局范围切换、索引化搜索、语义检索 |

PDF 的“原件已保存”与“能在原页准确批注”是两个不同的验收点。当前转换明确忽略图片和图形，只有 Markdown 正文不能支撑学术页码和区域批注。混合文字页与扫描页的 PDF 还需逐页标注覆盖情况，不能只凭整本有文字就认为全部可检索。

**实现建议与可行性**

先建立 Book、BookEdition、BookFile 和 ReadingState，让无正文书目也能存在。保留现有 MD／TXT 路径，增加 EPUB 的章节和稳定位置记录，PDF 增加逐页文字及坐标映射。封面、分类和阅读状态属于本地可控开发，可行性高。EPUB 和原页 PDF 阅读为中等复杂度，需要覆盖复杂排版与位置恢复。扫描 PDF 的 OCR 应复用学术模块的后台任务能力。

微信读书与豆瓣导入应先做候选审核和导入适配接口，再验证具体数据获取方式；它们依赖外部平台能力，当前不能承诺稳定自动同步。

代码依据：[阅读器](../../src/reader/ReaderOverlay.jsx)、[书籍服务](../../electron/books.cjs)、[PDF 转换](../../electron/book_pdf.py)、[原文定位](../../src/reader/readerPosition.js)。

### 3.2 学术文献库

当前只有通用书库和书籍摘录能力。功能路由中没有独立学术文献库，项目内也未发现可直接整合的 Aura 源码。文档描述的 Aura 能力属于拟整合基线，不能算作赛博书房已经实现。

| 需求组 | 当前基础 | 还需要实现 |
| --- | --- | --- |
| 空间入口与十个模块 | 现有场景功能路由和二维弹层框架 | 独立学术入口、精准热区、十模块导航、项目上下文 |
| 题录与全文 | 通用书籍文件导入和哈希 | Literature、Attachment、Edition；PDF／Word／RIS／BibTeX／DOI／ISBN；人工核对 |
| 书目检索 | 电影模块有豆瓣条目获取经验 | 图书豆瓣、Open Library、Crossref 适配及候选审核 |
| Zotero | 未发现产品内连接流程 | 本地 API、分类树、附件状态、手动增量同步、冲突记录 |
| 阅读与 OCR | 文字 PDF 转 Markdown、通用摘录 | 原页、区域批注、页码与坐标、Word 阅读副本、可恢复 OCR |
| 文献笔记 | 摘录批注可复用 | 按文献 Markdown 笔记、结构化区块、版本历史 |
| 引用与文稿 | 未发现对应实现 | 项目引用序列、CSL、脚注／文内引用／参考文献、DOCX 副本、Word／WPS 实时连接 |
| 运维与恢复 | 通用本地保存和部分导入状态 | 回收站、完整备份恢复、长任务恢复、跨模块搜索 |

**实现建议与可行性**

第一步应取得 Aura 的可编辑源码、依赖清单、许可和可运行样例，审查数据模型与目标 macOS 环境兼容性。本轮尝试访问文档引用的 Aura 指南未成功，因此未独立确认其能力和可复用程度。若暂时拿不到源码，可以先定义接口和导入标准，工期评估应按新增工作台处理。

最小研究闭环应是题录入库、关联 PDF、原页批注、文献笔记、生成参考文献并导出。十个模块可以分阶段开放，但不能用空页面充当完成。

Zotero 本地 API 有官方依据，可作为只读单向同步入口。实现时保存来源 ID、来源版本、本地修正与同步日志，附件不可访问时保留题录。[Zotero 官方 API 文档](https://www.zotero.org/support/dev/web_api/v3/basics)

Crossref 提供公开元数据查询，可用于 DOI 与题录匹配。搜索命中后仍应核对版本与字段，不能把元数据查询当作全文获取。[Crossref 官方文档](https://www.crossref.org/documentation/retrieve-metadata/rest-api/)

题录、RIS／BibTeX 和本地笔记可行性高；原页区域批注、OCR 恢复、CSL 和 DOCX 更新复杂度中高；Word／WPS 实时插入为最高不确定性，应先在目标软件版本上做最小连接试验，副本模式可先交付。

代码依据：[功能路由](../../src/scenes/featureBindings.js)、[书籍服务](../../electron/books.cjs)、[知识记录](../../src/data/knowledgeStore.js)。

### 3.3 个人知识库

| 需求组 | 当前实现 | 主要缺口 |
| --- | --- | --- |
| 来源与片段 | bookId、书名、摘录快照、章节／段落／文本范围等定位 | 跨媒介 SourceEntity、独立 SourceFragment、版本和失效标识 |
| 个人笔记 | 同一摘录多条批注，保留创建时间 | 自由笔记、电影影评、音乐感受、学术笔记、日记适配、综合输出 |
| 工作台 | 按书筛选、摘录列表、详情原文对照、回跳 | 文档要求的三栏工作台、类型／项目／时间／隐私筛选 |
| 搜索 | 书名、章节、摘录、批注、标签关键词匹配 | 跨模块全文索引、语义索引、搜索范围和相关性说明 |
| 关系 | 摘录关联书籍 | CitationLink、多来源引用、双向链接、反向链接、项目和关系图 |
| AI | 未发现对应产品链路 | 配置、上下文审核、日记单次授权、引用回答、用户确认保存 |
| 导出 | 当前筛选摘录及批注可导出 Markdown | 单条／批量／项目／对话输出、脚注、综合引用表 |
| 恢复 | Local Storage 保存 | 主数据迁移、版本、回收站、完整备份与索引重建 |

当前数据结构还保留 projects 字段，但当前知识库界面主要是摘录浏览，不能据此认定新版项目工作台已实现。

**实现建议与可行性**

先定义来源实体、来源片段、个人笔记与引用关系四个核心对象。电子书、学术、电影、音乐和日记通过适配器写入。一个模块保存笔记后，以稳定来源 ID 和版本号更新知识记录，重复触发不会生成重复条目。历史摘录应迁移为来源片段加批注，同时保留原 ID 映射和快照。

全文搜索先落地，再用本地嵌入模型建立可重建的语义索引。选型要依据中文检索质量、模型大小、首轮索引时间和目标设备内存实测。日记全文可参与本地索引，但外部 AI 上下文默认排除。

AI 放在引用链可验证之后。发送前展示具体片段，单次日记授权与会话绑定，保存 AI 回答时保留原回答、用户修改版、实际引用、模型和时间。聊天接口实现难度中等，可信引用、权限与恢复的复杂度更高。

代码依据：[知识库页面](../../src/features/KnowledgeWorkspace.jsx)、[知识记录](../../src/data/knowledgeStore.js)、[批注组件](../../src/reader/ExcerptAnnotations.jsx)。

### 3.4 音乐

音乐是当前外部接入基础最丰富的模块之一。源码已有 QQ／网易云登录与歌单读取、导入缓存、播放错误提示、上一首／下一首、进度、顺序／随机／单曲循环，以及关闭面板继续播放。

| 需求组 | 当前实现 | 主要缺口或冲突 |
| --- | --- | --- |
| 平台导入 | QQ／网易云账号、歌单和曲目流程 | 喜欢专辑专门入口、统一导入菜单、来源筛选、完整任务报告 |
| 本地上传 | 递归文件夹选择，支持多种音频后缀 | 当前对象 URL 只在本次打开有效，未长期保存本地曲目；缺文件标签读取、匹配与重新定位 |
| 数据组织 | 曲目带来源与歌单关系，同平台 ID 归并 | 专辑／歌手实体、跨源归组、来源记录、导入批次和候选匹配 |
| 浏览 | 左侧播放器、右侧歌单 | 全宽列表、紧凑播放器、陈列／列表双模式、分页和模式记忆 |
| 播放 | 持续挂载音频元素，面板关闭后继续播放；有恢复字段 | 来源切换与专辑队列的统一规则；丢失文件自动跳过与恢复 |
| 同步保护 | 可再次导入歌单 | 当前逻辑可能移除本次未返回且只属于该歌单的旧曲目，与保留收藏要求冲突 |
| 退出账号 | 有断开与缓存保留逻辑 | 未缓存的平台曲目可能被移除，应改为保留收藏并更新可播放状态 |

两个需要优先修正的代码路径分别是 savePlaylist 和 disconnect。前者重新导入时按新列表重组旧歌单，后者按是否缓存过滤曲目。这是静态代码发现，需要用“平台少返回一首歌”和“未缓存歌曲退出登录”的样例复现后修正。

**实现建议与可行性**

先区分“我的收藏记录”“平台歌单当前成员”和“音频可播放状态”，三者独立变化。平台取消喜欢只改变来源状态，收藏删除由用户显式触发。注销账号也只清除授权并标记需要重新连接。

本地音频应通过 Electron 保存可恢复文件引用或受控副本，读取内嵌标签与封面，并记录文件哈希。人工修正字段应有覆盖保护。随后建设专辑实体与全宽列表，再增加唱片抽取动画。跨平台归并只自动处理可靠匹配，翻唱、现场版和不同发行版进入待确认。

本地持久化、列表改造和专辑归组可行性高。账号接口、完整收藏范围、权限内播放和在线元数据匹配需要真实账号与网络验证。已有适配代码不能等同于各平台长期稳定保障。

代码依据：[音乐界面与同步](../../src/features/MediaCollections.jsx)、[平台导入界面](../../src/features/MusicSources.jsx)、[主进程接入](../../electron/music/register.cjs)、[缓存](../../electron/music/cache.cjs)、[常驻播放器入口](../../src/App.jsx)。

### 3.5 电影收藏

**实现建议与可行性**

先将 Movie、ViewingRecord、PersonalReview、PosterAsset 分开。豆瓣公共分数与个人星级保存在不同字段。旧来源链接迁入详情播放入口，旧个人文字进入本地笔记字段，外部更新只改来源字段。

详情页、影评编辑和知识入库可以先完成，本地可行性高。再做临时导入审核，四五星默认预选但允许调整；确认前不写入正式收藏。重复导入优先按豆瓣 ID 关联，同名不同年份或重拍版本不自动合并。手工海报优先级高于同步海报。

当前只证明存在单条豆瓣解析代码，已看列表获取和长期稳定性仍需单独验证。

### 3.6 地球仪

地球仪与最新设计的差距最大。当前能单张选择照片、填写地点和日期、显示记忆点并用滑杆旋转。照片存在 Local Storage，上传入口限制单张 2 MB。它尚未形成真实地理数据系统。

| 需求组 | 当前实现 | 主要缺口 |
| --- | --- | --- |
| 真实地点 | 地点文字和随机经度，点的纵向位置按序号排列 | 经纬度、EXIF、定位来源、无位置待确认、地图选点 |
| 照片管理 | 单张图片转数据 URL，按日期排序 | 批量／文件夹导入、原图／预览／缩略图、哈希去重、失效重关联 |
| 地球浏览 | CSS 球体与滑杆 | 全屏 3D 地球、真实坐标投影、远近聚合、搜索、连续镜头转场 |
| 旅程 | 未发现 | 建议、人工确认、拆分合并、时间序列路线和播放 |
| 世界风景 | 未发现 | 人工审核目录、图片来源和授权、独立图层、版本更新 |
| 想去 | 未发现 | 状态记录及用户确认转为已去过 |
| 知识关联 | 未发现 | 主动写成记忆笔记，回跳地点／照片／旅程 |
| 离线和恢复 | 图片在本地 | 离线城市目录、回收站、关系恢复、派生图清理 |

**实现建议与可行性**

第一步应停止给新照片生成随机位置。旧记录标为“位置未确认”，保留原地点文字与照片，请用户确认后再进入真实足迹图层。历史随机经度不能作为迁移后的真实坐标。

接着建立 Place、PhotoAsset、Journey，把日期分为拍摄时间与导入时间，保留 EXIF 与用户修正的来源。没有日期或位置的照片仍可保存在待整理区。先做好二维地图整理和批量导入，再用项目现有 Three.js 技术栈建设 3D 浏览。

旅程建议按时间间隔与地理距离形成候选，用户确认后才成为正式旅程。路线表示照片之间的访问顺序，日期不足时保留未知顺序。

真实坐标、照片文件化和手动整理可行性高；EXIF 差异、旅程建议与地图体验中等；大型照片库的 3D 聚合、转场和世界风景内容制作中高。公共图片授权审核是独立交付任务，应随风景包记录摄影者、来源、授权、版本和离线资产。

代码依据：[地球仪页面](../../src/features/SpaceLife.jsx)、[图片读取和存储](../../src/data/spaceStorage.js)、[场景入口](../../src/scenes/featureBindings.js)。

## 5. 共同实现方案

### 5.1 主数据与附件

建议逐步将主记录迁入支持事务的本地数据库，原件、海报、照片与音频放在受控文件目录中，界面通过现有 Electron 桥接访问。SQLite 是可评估的实现选项，选定前验证 Electron 打包兼容性和中文搜索效果。

保留当前可用书籍文件存储，先建立统一记录和相对附件引用，避免第一阶段同时推倒所有存储。Local Storage 可继续保存轻量界面偏好。照片和作品图不宜长期随整份记录反复序列化。

### 5.2 跨模块引用

最小协议包括来源 ID、来源类型、版本、片段快照、定位类型、定位内容、笔记 ID、创建及修改时间、隐私状态。

定位按媒介区分。PDF 保存页码与坐标，EPUB 保存章节及稳定文本锚点，Markdown 保存段落与文本范围，电影／音乐可以保存作品或时间点，地球仪保存地点、照片与旅程 ID。原文件失效后仍能查看快照，并清楚标明原文不可访问。

### 5.3 后台任务

导入、同步、转换、OCR、缩略图和索引统一采用任务记录。保存输入、进度、失败项、重试次数和输出版本。单项失败允许其他项继续，重复点击或重试不会重复创建记录。OCR 和语义索引在后台执行，编辑和阅读继续响应。

### 5.4 迁移与恢复

迁移前生成可恢复备份；保留旧 ID 映射；逐条迁移主记录和附件；校验数量、引用和文件可访问性；失败时保留旧库。备份先保障主数据、原件和关系，全文与向量索引可以重建。

知识库与地球仪文档将备份放到较后阶段。本报告建议把最小备份恢复提前，完整回收站和版本浏览可后续补齐。

## 6. 推荐交付顺序与通过条件

| 阶段 | 范围 | 必须通过的检查 |
| --- | --- | --- |
| A 基线与安全保存 | 冻结需求版本；统一最小协议；备份恢复；两项 P0 行为修正；Aura 与文稿连接探针 | 旧数据保留，空目录恢复可用；歌单变化不删除收藏；随机坐标不进入真实足迹 |
| B 本地日常体验 | 音乐持久化与全宽列表；书架状态；电影详情和影评；照片真实归档 | 重启、断网、重复导入均可解释且不丢内容 |
